## 一、前置

Sprint 2B 交付了 Core Engine MVP（录入→查看→AI 复习→判题），当前状态机停留在`未复习→已复习`。Sprint 3 补完剩余状态转换：`已复习→已掌握` 和 `已掌握→未复习（回滚）`。

**全局 Roadmap 对应（来自 LearningOS Spec/prd.md §7）：**

| 版本 | 内容 | 当前状态 |
|:---:|------|:---:|
| v0.1 | 录入、查询、Review（MVP） | ✅ Sprint 2B 完成 |
| **v0.2** | **已掌握状态（AI 出题+记忆曲线）、二次错误回滚** | **⏳ Sprint 3** |
| v0.3 | 学习仪表盘 | 规划中 |

## 二、垂直切片设计

```
Slice 1（状态机闭环）：   状态判定逻辑 → 已掌握命令(mkt master) → 记忆曲线调度
Slice 2（二次错误回滚）：  录入检测回滚 → 根因探究命令(mkt recall) → 概念讲解输出
Slice 3（基础设施完善）：  mkt add --raw → AI Provider 配置化 → check 持久化 → 测试全补
```

### 为什么这个顺序

已掌握是状态机的终点——先从它开始闭环。二次错误回滚依赖已掌握状态（没有"已掌握"就没东西可回滚）。基础设施完善（add --raw / check 持久化）可与非阻塞并行。

## 三、Task 分解

---

### T1 · 已掌握状态判定 — 核心逻辑（core/service.py + core/ai.py）

**PRD 映射：** §6 Beyond MVP P1 — "已掌握状态（AI 出题 + 记忆曲线间隔测试）"
**CONTEXT 映射：** Status 定义 "已掌握：系统按记忆曲线出题，正确率达标"

#### 设计说明

已掌握≠人工判定。它是系统基于**间隔出题 + 正确率**的客观判定。MVP 简化为：

1. **触发条件**：一个 topic 下所有 Mistake 均为`已复习`状态 → 可触发已掌握测试
2. **测试方式**：AI 生成 5 道间隔测试题（覆盖该 topic 的核心概念 + 易错点）
3. **判定规则**：5 题全对 → `已掌握`；否则保持`已复习`，错题转为新 Mistake
4. **记忆曲线（MVP 简化）**：已掌握后，按间隔（7 天 → 30 天 → 90 天）自动提醒复测

#### 新增 CLI 命令

```
mkt master --student 开心 --topic 分数加法
```

输出：测试题（不含答案）+ 判定结果

**依据：** Constitution A5（温故）要求"持续帮助学生巩固、迁移与应用已有知识"。A8（可溯）要求判定有依据——间隔测试结果就是依据。

#### 函数新增

| 文件 | 函数 | 职责 |
|------|------|------|
| `service.py` | `master_topic(student, topic)` | 检查 topic 是否全部已复习 → 调用 AI 出 5 题 → 返回测试 |
| `ai.py` | `generate_mastery_test(mistakes, profile)` | 生成间隔测试题（含审题点） |
| `service.py` | `judge_mastery(session)` | 判定：全对→已掌握，有错→保持已复习 |

#### 存储变更

`knowledge_map` 新增 `next_review` 字段：

```yaml
knowledge_map:
  分数加法:
    mistake_count: 5
    last_reviewed: 2026-06-29
    mastered: true
    next_review: 2026-07-06  # MVP：7 天后复测
```

### T2 · 二次错误回滚 + 根因探究（core/service.py + core/ai.py + cli/main.py）

**PRD 映射：** §6 Beyond MVP P1 — "二次错误回滚 + 根因探究 + 概念讲解流程"
**CONTEXT 映射：** 二次错误规则 — "已掌握的 Mistake，若同 Student + 同类型出现新错题 → 自动回滚"

#### 设计说明

当 Parent 录入新错题时：
1. `add_mistake` 检测该 student + topic 下是否有 Mistake 处于`已掌握`状态
2. 若有 → 自动回滚该 topic 下所有`已掌握` Mistake → `未复习`
3. 系统建议 Parent 运行 `mkt recall` 进行根因探究

#### 新增 CLI 命令

```
mkt recall --student 开心 --topic 分数加法
```

输出：根因分析 + 概念讲解（AI 生成）

**依据：** Constitution A7（过程优先）要求"保存学生的思考过程、错误过程与修正过程"——二次错误不是简单退回，而是需要深入理解为什么再次出错。

#### 函数新增

| 文件 | 函数 | 职责 |
|------|------|------|
| `service.py` | `_detect_rollback(mistake)` | 录入检测：该 topic 是否有已掌握 Mistake → 自动回滚 |
| `ai.py` | `generate_root_cause(mistakes, profile)` | AI 分析：为什么已掌握的知识点又错了 |
| `cli/main.py` | `cmd_recall` | mkt recall 入口 |
| `profile.py` | `update_knowledge_map` 扩展 | 回滚时更新 mastered 和 next_review |

### T3 · `mkt add --raw` 批量导入（core/service.py + cli/main.py）

**来源：** Sprint 2B 审计 #4（Auditor Hermes 建议，Planner 以 R2+R3+R5 异议后延迟到 Sprint 3）

#### 设计说明

```
mkt add --raw <文件.md> --student 开心 --grade 五年级上 [--confirm]
```

流程：
1. 读取 MD 文件内容
2. 调用 AI 提取：subject、topic、question、wrong_answer、correct_answer、reason
3. 提取结果预览（不确认模式）或自动写入（--confirm）
4. 逐条调用 `add_mistake`（复用已有逻辑）

**R5 合规说明：** Sprint 3 中 AI Core 已有 Sprint 2B 的充分测试验证（mock 路径），此时引入 AI 提取的确定性风险可通过 `--confirm` 标志让 Parent 逐条确认缓解。AI 提取结果仅作为预览，确认后才写入——录入的最终真实性由人确认（符合 A12 诚信）。

## 六、风险点

| # | 风险 | 缓解 |
|:---:|------|------|
| R1 | **AI 间隔测试题质量不可控** — 生成的 5 道题可能过难或过易 | 在 prompt 中显式要求"覆盖核心概念 + 易错点"；同时提供已掌握的错题列表作为参考 |
| R2 | **记忆曲线时间计算** — MVP 简化版（7/30/90 天）可能不符合真实遗忘规律 | 标记为 MVP 简化，不引入复杂算法。真实记忆曲线（SM-2 等）v0.3+ 考虑 |
| R3 | **AI Provider API 不可用** — 网络问题或 key 无效 | 降级策略：返回 mock 结果 + 告警日志，系统不崩溃 |
| R4 | **add --raw AI 提取错误** — 提取的字段与实际不符 | --confirm 预览机制 + 明确提示"请核对" |

## 十、待确认

1. **`next_review` 的持久化方式**：写入 profile.yaml 的 knowledge_map 中，与 mastered 并列。已掌握判定的当天设置 next_review = today + 7（天）。到期后如何提醒？MVP 不做主动提醒，Parent 自行决定何时 `mkt master`。
2. **`mkt add --raw` 的 MD 输入格式**：暂定每道错题格式为 `## 题目 ❌\n- **错误答案：** \n- **正确答案：** \n- **原因：**`——与 Sprint 2B 的 Mistake 序列化格式一致。其他格式由 AI 模糊解析。
3. **AI Provider 默认值**：环境变量 `AI_PROVIDER` 默认 `"mock"`（保持 Sprint 2B 行为不变），设置为 `"openai"`、`"anthropic"` 或 `"deepseek"` 时读取 `AI_API_KEY` 并启用真实 API。这样的默认值确保新开发者 clone 后可直接运行不报错。
