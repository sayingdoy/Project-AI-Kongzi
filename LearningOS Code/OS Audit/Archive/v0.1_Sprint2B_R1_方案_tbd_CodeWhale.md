Phase 2A（Kongzi）交付了完整规范链：PRD → Architecture → ADR。Phase 2B（本次）实现 Core Engine 所有代码，跑通两条垂直切片。

Phase 2A 审计报告（Hermes）移交时提到 JSONL 格式和 `data/{student}/mistakes.jsonl`，但**最终 Architecture §6 和 ADR-002 已裁定为 Markdown + Frontmatter**。本方案以最终 Spec（Architecture + ADR）为准，非 2A 中间审计意见。下文每项决策引用当前 Spec 段落。

## 二、垂直切片设计

```
Slice 1（录入→查看）：   T1 → T2(读+追加+ID查询) → T4(add+list+get) → T7(add+list+show) → T8(前4个测试)
Slice 2（AI 复习）：      T2(update+session) → T5 → T4(review+check) → T6 → T7(review+check+profile) → T8(全部)
```

### 为什么先做录入→查看

1. **数据流闭合**：从 CLI 输入到文件落地再到 CLI 输出，一条完整的用户故事先跑通（AGENTS.md §8.3-1 "先跑通第一条完整数据流"）
2. **降低风险**：文件读写逻辑（Frontmatter 解析/生成、追加写入）是系统最复杂的基础设施，先验证这部分，再叠 AI 层时只需关注 AI 接口的正确性
3. **测试先行**：Slice 1 完成后 repository 和 service 的核心路径已测试覆盖，Slice 2 的 AI 集成可在已知稳定的地基上开发

#### T1 · 数据模型（`core/models.py`）

**依据：** Architecture §3 模块结构定义 models.py；ADR-002（Markdown+Frontmatter）决定序列化格式；Architecture §6.1 定义错题文件格式。

**范围：**

| 类 | 字段 | 说明 |
|------|------|------|
| `Mistake` | `id`, `student`, `subject`, `grade`, `topic`, `question`, `wrong_answer`, `correct_answer`, `reason`, `status`, `created_at`, `source` | 对应 Architecture §6.1 格式 |
| `ReviewSession` | `id`, `student`, `topic`, `grade`, `date`, `exercises`, `result` | 对应 Architecture §6.2 格式 |
| `Exercise` | `id`, `question`, `student_answer`, `correct_answer`, `passed` | 嵌入 ReviewSession |
| `Profile` | `name`, `grade`, `subjects`, `knowledge_map`, `learning_trends` | 对应 CONTEXT Profile 结构 |

**序列化要求：**
- `Mistake.to_markdown_entry()` → 生成 `## 日期 · 题目 ❌` 格式条目（§6.1）
- `Mistake.from_markdown_lines(lines)` → 逆向解析
- `ReviewSession.to_frontmatter()` / `from_frontmatter()` → Frontmatter YAML 序列化

**验收标准：**
1. 每个 dataclass 可正常构造、类型正确
2. `Mistake.to_markdown_entry()` 输出的字符串能被 `from_markdown_lines()` 完整还原（双向序列化对称）
3. 状态枚举值仅限于 CONTEXT 定义：`未复习` | `已复习` | `已掌握`
4. 错误原因枚举仅限于 CONTEXT 定义：`概念不清` | `审题错误` | `计算错误` | `方法错误` | `粗心` | `未掌握`

#### T2 · 文件读写（`core/repository.py`）

**依据：** Architecture §4 数据流定义了 write/read/append 操作；Architecture §6 定义了文件格式；ADR-002 确认 Markdown+Frontmatter 存储；CONTEXT §File System Convention 定义了路径规则。

**不创建 validator.py（与 sprint-plan 的差异说明见下文 T3 段）。**

**函数列表：**

| 函数 | 职责 | 依据 |
|------|------|------|
| `read_mistakes(student, subject, grade, topic)` | 读取一个 .md 文件中所有 Mistake 条目 | §6.1 格式，按 Frontmatter topic 定位文件 |
| `append_mistake(mistake)` | 追加一条 Mistake 到对应 .md 文件末尾，更新 Frontmatter `mistake_count` | §4.1 录入流 step 5-7 |
| `update_mistake_status(mistake_id, new_status)` | 改写文件内指定 Mistake 的状态字段 | §4.3 判题流 step 4 |
| `find_mistake_by_id(mistake_id)` | 跨文件搜索指定 ID 的 Mistake | §4.2 复习流需要定位 |
| `read_profile(student)` | 读取 profile.yaml | CONTEXT Profile 结构 |
| `write_profile(student, profile)` | 写回 profile.yaml | 同上 |
| `create_review_session(session)` | 创建 ReviewSession 文件 | §4.2 复习流 step 5 |

**路径约定（Architecture §4 + CONTEXT File System Convention）：**

Repository 以可配置的 `BASE_DIR` 为基准（默认 `../../LearningOS Users/` 相对于模块目录），所有路径按此解析：

```
{BASE_DIR}/{student}/data/错题整理/错题集/{subject}/{grade}/{topic}.md
{BASE_DIR}/{student}/data/错题整理/复习记录/{subject}/{grade}/{date}_{topic}.md
{BASE_DIR}/{student}/profile.yaml
```

**禁止硬编码绝对路径**（AGENTS.md §5 约束）。

**Frontmatter 操作规范：**
- 追加时：若文件不存在 → 写入完整 Frontmatter 头 + 第一条 Mistake
- 追加时：若文件存在 → 读取 Frontmatter → 更新 `mistake_count` 和 `last_updated` → 重写 Frontmatter → 追加条目
- 状态更新时：使用 `id` 匹配条目，定位后替换该条目的状态行

**验收标准：**
1. `append_mistake` → 文件不存在时创建含 Frontmatter 的文件，存在时追加条目并更新计数
2. `read_mistakes` → 返回该文件内所有 Mistake 对象的列表
3. `find_mistake_by_id` → 跨科目/年级/知识点搜索，返回匹配的 Mistake
4. `update_mistake_status` → 只修改状态行，不改变其他内容
5. 所有操作使用 `tmp_path` 可验证

#### T3 · 校验逻辑（放入 `core/service.py`，不独立成文件）

**依据：** Architecture §3 的层结构中 Service 的职责包含"校验"。Architecture 文件列表未列出 `validator.py`。依据 **R2（简洁优先）**，不因"可能未来"提前创建独立文件。PRD §4 F1 要求的三项校验在 Service 层实现为私有函数。

**与 sprint-plan.md 的差异：** sprint-plan.md 列出了 T3 `core/validator.py`。Planner 评估后认为 Architecture（Spec 链的更高层）未定义该文件，且 R2（简洁优先）反对为三个验证函数提前建模块。**将验证逻辑内联为 `service.py` 的私有函数。**

| 私有函数 | 职责 | 依据 |
|------|------|------|
| `_validate_topic(topic)` | 查 `knowledge-points.yaml`，确认 topic 在预定义列表中 | PRD F1、ADR-003 |
| `_validate_reason(reason)` | 查受控词汇（CONTEXT §Reason） | PRD F1、CONTEXT |
| `_validate_subject(subject)` | 查受控科目列表 | CONTEXT §Subject |

**验收标准：**
1. 非法 topic → 抛异常或返回明确错误信息
2. 非法 reason → 同上
3. 合法输入 → 通过

#### T4 · 业务逻辑（`core/service.py`）

**依据：** Architecture §4.1（录入流）、§4.2（复习流）、§4.3（判题流）。

**Slice 1 范围（仅录入+查看）：**

| 函数 | 流程 |
|------|------|
| `add_mistake(student, subject, grade, topic, question, wrong, correct, reason)` | 校验三个输入 → 生成 UUID8 ID → 构造 Mistake → 调用 Repository.append_mistake |
| `list_mistakes(student, **filters)` | 读取指定 student 的所有错题文件 → 按 filters 筛选 → 返回列表 |
| `get_mistake(mistake_id)` | 调用 Repository.find_mistake_by_id → 返回单个 Mistake |

**Slice 2 范围（复习+判题，见后文叠加说明）：**

| 函数 | 流程 |
|------|------|
| `review(student, topic)` | 读取 topic 下未复习 Mistake + 读取 Profile → 调用 AI → 创建 ReviewSession |
| `check(exercise_id, correct)` | 查找 ReviewSession → 标记结果 → 判定 → 更新状态或创建新 Mistake |

**UUID8 生成策略：** 使用 `uuid.uuid4().hex[:8]`，短 ID 便于 CLI 交互。碰撞概率在 MVP 数据量下可忽略。

**验收标准（Slice 1）：**
1. `add_mistake` 成功 → 文件被创建/追加，返回 Mistake 对象带有效 ID
2. 非法输入 → 抛异常，不写文件
3. `list_mistakes` → 返回过滤后的 Mistake 列表（未传入 filter 时返回全部）
4. `get_mistake` → 根据 ID 返回正确 Mistake；不存在的 ID 抛异常

#### T5 · AI 集成（`core/ai.py`）— Slice 2 实现

**依据：** Architecture §5（AI Integration）、PRD §5 F3。

| 函数 | 职责 |
|------|------|
| `analyze_and_generate(mistakes, profile)` → `ReviewContent(dict)` | 构造 prompt → 调用 AI → 解析返回的归纳+引导+3 道题 |

**AI Provider 设计：** 遵循 Architecture §5 和 CONTEXT "AI Provider（MVP）" 定义 — 默认复用调用 Agent 的模型，不做 Provider 抽象层。提供 `ai_call(prompt, system_prompt)` 内部函数，未来可扩展。

**Prompt 结构（Architecture §5）：**

```
System Prompt = Constitution A1-A12 核心条款 + Student Profile（name, grade, knowledge_map）
User Message  = 错题列表（题目+错误答案+正确答案+原因）+ 任务要求
```

**输出解析：** AI 返回结构化文本 → 提取 `summary`（错误归纳）、`guiding_questions`（引导问题列表）、`exercises`（练习题列表）→ 构造 ReviewContent。

**验收标准：**
1. 构造的 prompt 包含 Constitution A1 内核（启发，不直接给答案）
2. 返回的 ReviewContent 包含 3 个字段且类型正确
3. 输出练习题不带答案（因为 A1 要求"不给答案"，但 Architecture §6.2 示例中练习题的格式实际上是题目+参考答案用于家长核对——需确认是否统一。本方案采用：AI 返回题目+参考答案，Core 输出给家长时显示题目，参考答案仅用于后续 `mkt check` 判题，Parent 可见。这符合 A1 的"不给学生答案"和"家长可核对"的实际需求。）

#### T6 · 画像管理（`core/profile.py`）— Slice 2 实现

**依据：** CONTEXT Profile 结构、PRD §5 F6。

| 函数 | 职责 |
|------|------|
| `update_knowledge_map(profile, mistakes, session_result)` | 基于本次复习结果更新该 topic 的 mistake_count、last_reviewed、common_reason 和 mastered 状态 |
| `detect_trends(profile, mistakes)` | 分析历史错误模式 → 返回 learning_trends（含 source 字段指向原始 Mistake ID） |

**约束：** 所有 insight 必须有 `source` 字段（A8 可溯性）。禁止主观标签（CONTEXT Profile 约束）。

**验收标准：**
1. `update_knowledge_map` → knowledge_map 的该 topic 条目正确更新，证据字段完整
2. `detect_trends` → 返回的 trend 含 `pattern`、`since`、`source` 三个字段
3. 不产生任何主观标签

#### T7 · CLI 入口（`cli/main.py`）

**依据：** Architecture §3 模块结构、PRD §4.

**命令结构（argparse）：**

```
mkt add       --student STR --subject STR --topic STR
              --question STR --wrong STR --correct STR --reason STR

mkt list      --student STR [--subject STR] [--topic STR] [--status STR] [--grade STR]

mkt show      --id STR

mkt review    --student STR --topic STR                  # Slice 2

mkt check     --id STR --correct | --wrong                # Slice 2

mkt profile   --student STR                               # Slice 2
```

**CLI 设计原则（Architecture ADR-004）：** CLI 是 Core Engine 的薄壳。每个命令解析参数后调用 `service.*()` 函数，打印结果，不做业务逻辑。错误处理输出中文可读消息。

**验收标准：**
1. `mkt add` 带齐参数 → 成功录入 → 打印 Mistake ID
2. `mkt add` 缺少参数 → 打印使用帮助
3. `mkt list` → 表格/列表形式打印匹配的 Mistake
4. `mkt show --id <id>` → 打印单个 Mistake 详情
5. 未知命令 → 打印帮助

## 五、风险点

| # | 风险 | 缓解 |
|:---:|------|------|
| R1 | **Frontmatter 解析/重写逻辑错误** — Markdown 文本操作易出错，尤其是追加写入时更新 Frontmatter | 测试使用 tmp_path + 样本文件做解析-写入-重新解析的三段式验证 |
| R2 | **AI 输出非结构化** — AI 返回的文本格式不稳定，导致解析失败 | ai.py 内对 AI 输出做校验和 fallback 处理（重试 1 次 + 默认值兜底） |
| R3 | **多文件 ID 搜索性能** — `find_mistake_by_id` 需跨多个 .md 文件搜索，数据量大时慢 | MVP 数据量小，线性扫描够用。加上文件级缓存（文件 mtime 未变则复用读取结果） |
| R4 | **AI Prompt 中的 Constitution 约束** — 若不显式约束，AI 可能直接生成答案而非引导 | 在 System Prompt 中显式包含 A1 原文：MUST NOT 替学生完成思考过程，MUST 提供提示与引导 |

## 六、不做（范围排除）

依据 PRD §5 MUST NOT + Constitution A6、A9 仲裁原则。

| 排除项 | 原因 | 依据 |
|------|------|------|
| Web UI / HTTP 服务器 | MVP 命令行为主 | PRD §5 MUST NOT |
| 学生直接交互（AI 对话辅导） | MVP 只有 Parent<br/>操作 | PRD §5 MUST NOT |
| 已掌握状态的记忆曲线调度 | v0.2 功能 | PRD §6 Beyond MVP |
| 二次错误回滚 + 根因探究流程 | v0.2 功能，依赖已掌握状态 | PRD §6 Beyond MVP |
| 语文/英语知识点扩展 | MVP 仅数学 | knowledge-points.yaml 现状 |
| SQLite 或其他数据库 | Markdown+Frontmatter 已定 | ADR-002 |
| AI Provider 抽象层（多 Provider 适配）| MVP 复用 Agent 模型即可 | Architecture §5 + R2（简洁优先）|
| 并发/锁机制（多 Agent 同时写入）| MVP 单用户串行操作 | Architecture §8 Q1 标记为后续 ADR |
| `.gitignore` 配置调整 | Phase 2A 已设 | — |
| 项目配置文件（pyproject.toml/requirements.txt） | Phase 2A 已设 | — |
| 不修改 Constitution / CONTEXT / Spec | 最高原则不可动 | AGENTS.md §5 禁止事项 |
| 不修改 LearningOS Spec/ 或 modules/*/Spec/ | 规范层不可动 | 运行时 AGENTS.md §4 |
