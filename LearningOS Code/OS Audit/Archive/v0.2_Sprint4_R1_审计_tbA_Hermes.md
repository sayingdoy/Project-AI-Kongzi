## 审计发现

### #1 ⚠️ Trend 数据一致性 — 先补 ReviewSession 完整性

**方案原文（R1 缓解）：**

> "`mkt trend` 从 Mistake 的 created_at + profile 状态变更推断，ReviewSession 作为辅助。不依赖 session 全记录。"

**问题：** ReviewSession 是状态变更的唯一审计证据（A12）。如果 session 记录不全，trend 输出的"复习通过""已掌握"等事件就是推断而非证据。这违反了 A8（可溯）。

**根因：** Sprint 2B/3 的 `mkt review` 和 `mkt verify` 是否真的写入了 ReviewSession 文件？Sprint 3 的 "check 持久化" 只修复了 `mkt check` 的持久化。但 `mkt review` 和 `mkt verify` 创建 session 的逻辑是否正确，未经验证。

**建议：** 在实现 T2 之前，先跑一条完整数据流验证——
```
mkt review → 确认 ReviewSession 文件存在 → mkt check → 确认 session 更新 → mkt verify → 确认 session 存在
```
如果这 4 步有缺失，先修复，再做 trend。

→ **先验证数据完整性，再消费数据。**

---

### #2 ⚠️ 推荐算法缺少"无推荐"场景的边界条件

**方案原文（T3 验收标准 #1）：**

> "至少输出 1 条推荐（有任意数据时）"

**问题：** "有任意数据时"太宽。如果所有 topic 都已掌握且未到复测期，推荐引擎应输出"暂无推荐，继续保持！"而非强行推荐一个不需要复习的 topic。

**建议：** 
- 推荐指数 < 30% 的 topic 不显示（即使有数据）
- 如果 Top-3 的推荐指数都 < 30%，输出"暂无推荐"而非强行凑 3 条

→ **修正 T3 验收标准 #1 和 #3。**

**事实：** Sprint 3 方案包含 `test_cli.py` 但未交付。Sprint 4 方案再次列出 test_cli.py。

---

### #4 📝 科目列表和 `mkt add` 默认 subject 行为

**当前行为（推断）：** `mkt add` 的 `--subject` 参数可能没有默认值或默认="数学"。多学科后，Parent 每次都要写 `--subject 英语` 增加操作负担。

**建议：** 不做代码变更。在 SOP.md 更新 Sprint 4 操作说明时，每条命令示例明确标注 `--subject`。未来 Web UI 用下拉框解决这个问题。
