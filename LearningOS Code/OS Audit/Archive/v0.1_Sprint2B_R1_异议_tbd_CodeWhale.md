## 二、异议列表

### 异议 1：`mkt add --raw` 批量导入命令

| 字段 | 内容 |
|------|------|
| **审计方原文** | "在 Slice 1 中新增一个命令变体：`mkt add --raw 文件.md --student 开心 --grade 五年级上`。流程：读取 MD 文件内容 → 调用 `ai.py` 提取字段 → 构造 Mistake → 走正常 `add_mistake` 流程。工作量：T4 `service.py` 加一个方法，复用已有 AI 调用。不推迟 Sprint。" |
| **执行方观点** | 此建议超出 Sprint 2B MVP 范围，在 Slice 1 植入对 AI 模块（T5）的依赖，破坏两条垂直切片的隔离性。 |
| **准则依据** | **R2（简洁优先）**—"绝不为了未来的'可能性'而提前添加功能或抽象。如果一位资深工程师会认为这个设计'过度复杂'，就必须停下来并提议简化。"Owner 的扫描仪→PaddleOCR→MD 是未来计划，不在 MVP MUST 列表（PRD §5），当前 4 个 User Story 均不涉及批量导入。提前在 Slice 1 引入非确定性 AI 解析，资深工程师会判断为过度工程。<br><br>**R3（精准修改）**—"每处改动都必须能直接追溯到用户的具体需求。"`--raw` 无对应 Task（T1-T8 均不涉及），无对应 User Story（US1-US4 均不涉及），无对应 PRD MUST（F1-F6 均不涉及）。本轮 Sprint 不应引入无需求追溯的改动。<br><br>**R5（确定性事务用代码）**—"业务逻辑（如重试、路由）必须由确定性代码处理，而非依靠模型来决定。"录入是系统的数据根基（A12 诚信："忠实记录学生真实的学习过程"），AI 提取是非确定性操作——同一 MD 文件两次可能得到不同解析结果。将 AI 引入录入流程违反 A12 的证据真实性要求。<br><br>**附加理由：** Slice 1 的设计契约是"在不依赖 AI 的前提下验证数据流"。引入 `--raw` 后，`add_mistake` 的计算路径出现分支：确定性路径（逐字段）和 AI 路径（MD→AI→字段），Slice 1 验收时需同时验证两条路径，而 AI 路径依赖尚未实现的 T5。 |
| **替代方案** | 不反对 `--raw` 功能本身的价值。建议保留为 **Sprint 3 或 v0.2** 特性，届时 AI Core（Slice 2 已验证）可直接复用，且录入流程的确定性分支已完成充分测试。可在 CLI help 文本中预留签名作为占位符，不实现逻辑。 |
