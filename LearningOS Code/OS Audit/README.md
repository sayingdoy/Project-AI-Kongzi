# OS Audit — 代码审计工作流

> 乙方做方案、甲方做审计。多轮交叉验证，Karpathy 准则为最高宪法。
> **本工作流遵循 `audit-os` skill v2.0。**
> 本目录名为 `OS Audit/`（非 skill 默认的 `Project Audit/`）。
> v2.0 合并了 Hermes built-in `system-audit` 的成熟内容，已部署到共享仓库 `/c/Users/Admin1/.agents/skills/audit-os/`，所有 Agent（Hermes / MiMo / Darwin）均可通过 `skill_view('audit-os')` 加载。

## 一、角色定义

| 角色 | 职责 | 产出物 |
|------|------|------|
| **Planner**（乙方/执行方） | 出方案：识别问题、设计解法、排执行计划 | 方案（R1/R2…）、异议响应、终版方案 |
| **Auditor**（甲方/审核方） | 审方案：架构合理性、Karpathy 合规性、范围/风险 | 审计报告 |
| **Integrator**（任意方） | 多方评审合并，Karpathy 准则校准 | 方案整合报告 |

## 二、审计流程

```
Round 1                                     Close
───────                                     ─────

Planner →  方案_tbd         →  终版_OK
  ↓                              ✅
Auditor →  审计_tbA
  ↓
     ├── Planner 全部采纳 → 终版
     └── Planner 有异议 → 异议_tbd
                              ↓
                          Auditor 复审
                              ↓
                          ├── Auditor 让步 → 终版
                          └── 仍分歧 → Owner 裁决

（如有多轮审计，重复上述过程）
```

### 2.1 Round 1：方案提出 + 审计

1. Planner 提交方案 → 文件后缀 `_tbd`（待执行）
2. Auditor 独立审计 → 文件后缀 `_tbA`（待 Planner 确认采纳）
3. Planner 阅读审计报告，逐项标注"采纳"或"异议"

### 2.2 异议响应（Planner 权利）

Planner 对审计建议有异议时，提交异议响应文件：
- 文件后缀 `_异议_tbd`
- **必须逐项引用 Karpathy 准则**（不能只说"我觉得不对"）
- 每项异议必须包含：审计建议原文 → 执行方观点 → 准则依据 → 替代方案
- 已采纳的建议也列出，标注"已修正"，但不需要进入异议流程

### 2.3 复审与裁决

4. Auditor 阅读异议响应：
   - **认为执行方有理** → 让步，更新审计结论，分歧清零
   - **认为审计方有理** → 维持原建议，双方仍分歧
5. **仍分歧** → 提交项目 Owner 裁决。Owner 以 Karpathy 准则为终裁依据
6. 分歧清零 → Planner 出终版方案，后缀 `_OK`

### 2.4 闭环（归档 → 编码）

> **硬闸门：终版方案产出 → 归档 → 更新 audit_log.md → 方可开始编码。**
> 禁止在归档前执行任何代码变更。

7. Planner 确认终版：
   - 出 `{版本}_{内容}_终版_OK_{Planner}.md`
   - 将本轮审计**所有文件**（方案、审计、异议响应、终版）一并移入 `Archive/`
   - 更新 `audit_log.md`（记录决策链）
   - 根目录仅保留**正在审计轮次中**的文件（状态为 `tbd` 或 `tbA`）
8. **归档完成后，Planner 开始编码。**

### 2.5 闭环 Checklist

每轮审计结束时，双方确认：

| # | 检查项 | 谁 | 状态 |
|:---:|------|:---:|:---:|
| C1 | 分歧清零 | Auditor | |
| C2 | 终版方案已写入 `Archive/` | Planner | |
| C3 | 本轮全部审计文件已移入 `Archive/` | Planner | |
| C4 | `audit_log.md` 已更新 | Planner | |
| C5 | OS Audit 根目录仅剩进行中文件 | Planner | |
| C6 | 编码已开始 | Planner | |

## 三、文件命名规范

```
{版本号}_{简要内容}_R{轮次}_{类型}_{状态}_{执行方/审核方}.md
```

### 3.1 字段说明

| 字段 | 说明 | 示例 |
|------|------|------|
| 版本号 | 目标升级版本 | `v1.5.1` |
| 简要内容 | 方案主题（中文，用下划线连接） | `维护协议`、`综合改进计划` |
| R{轮次} | Round 编号 | `R1`、`R2`（终版用 `终版`） |
| 类型 | 文件类型 | `方案`、`审计`、`异议`、`终版` |
| 状态 | 生命周期标记（见下表） | `tbd`、`tbA`、`OK` |
| 执行方/审核方 | 产出者 | `MiMo`、`Hermes` |

### 3.2 类型与状态对照

| 类型 | 状态 | 产出者 | 说明 |
|------|:---:|:---:|------|
| `方案` | `tbd` | Planner | 方案已提交，等待 Auditor 评审 |
| `审计` | `tbA` | Auditor | 审计已提交，等待 Planner 确认采纳 |
| `异议` | `tbd` | Planner | Planner 对审计建议有异议，等待 Auditor 复审 |
| `终版` | `OK` | Planner | 分歧清零，终版方案 |
| `审计` | `OK` | Auditor | Auditor 让步后更新的终版审计 |

### 3.3 完整生命周期示例

```
# Step 1: Planner 提交方案
v1.5.1_维护协议_R1_方案_tbd_MiMo.md

# Step 2: Auditor 提交审计
v1.5.1_维护协议_R1_审计_tbA_Hermes.md

# Step 3: Planner 有异议，提交异议响应
v1.5.1_维护协议_R1_异议_tbd_MiMo.md

# Step 4: Auditor 复审（让步或维持）
#   a. 让步 → 终版
#   b. 维持 → Owner 裁决后再终版
v1.5.1_维护协议_终版_OK_MiMo.md

# Step 5: 归档（Planner 执行）
Archive/
├── v1.5.1_维护协议_R1_方案_tbd_MiMo.md
├── v1.5.1_维护协议_R1_审计_tbA_Hermes.md
├── v1.5.1_维护协议_R1_异议_tbd_MiMo.md
└── v1.5.1_维护协议_终版_OK_MiMo.md
```

### 3.4 归档规则

- **根目录**：仅存放状态为 `tbd` 或 `tbA` 的文件（正在审计轮次中）
- **Archive/**：状态 `OK` 的终版方案 + 其关联的所有轮次文件
- **归档时机**：Planner 阅读完终版审计报告，确认终版方案后，**一并移入** Archive/
- **归档执行者**：Planner（执行方）

### 3.5 既有文件

已完成的审计文件已在 `Archive/` 中——作为历史决策链保留，不改名。

## 五、审计检查清单

Auditor 在每轮评审中必须覆盖以下维度：

### 5.1 架构合理性

- [ ] 模块化：是否存在单体膨胀？职责是否清晰？
- [ ] 数据模型：分类体系是否统一？数据流是否可追溯？
- [ ] 扩展性：新功能的依赖是否已声明？是否有未识别的前提条件？
- [ ] 技术债：是否在已有债上叠加功能？重构预算是否充足？

### 5.2 Karpathy 合规性

| 准则 | 检查点 |
|------|------|
| R1 先思考再编程 | 假设是否显式声明？不确定处是否标注？ |
| R2 简洁优先 | 是否存在为"可能未来"提前的抽象？是否有过度工程化？ |
| R3 精准修改 | 每处改动是否追溯到具体需求？是否有顺手优化？ |
| R4 目标驱动 | 成功标准是否定义？是否有验证步骤？ |
| R5 确定性逻辑 | 业务逻辑是否由代码而非模型处理？ |
| R8 先读再写 | 是否阅读了受影响模块的调用者和依赖？ |
| R9 测试意图 | 测试是否在业务逻辑改变时失败？ |
| R10 检查点 | 多步骤任务是否有阶段性总结和验证？ |
| R12 审计追溯 | 变更是否可验证可回退？ |

### 5.3 范围与风险

- [ ] 是否有 scope creep（范围蔓延）？
- [ ] 是否有未声明的前提依赖？
- [ ] 工时估算是否合理？
- [ ] 推迟到下一版本的功能是否有明确清单？

## 七、Karpathy 准则在审计中的角色

Karpathy 12 准则是审计的**最高宪法**。分歧无法达成共识时，以 Karpathy 准则为终裁依据，引用具体规则编号。

- **例**：Shell 重写争论 → R2（简洁）+ R3（精准）→ 保留不动的裁决成立。
- **例**：版本号精简争论 → 数据溯源价值 vs 维护成本 → R2（不是过度工程化，零维护成本）→ 保留的裁决成立。
